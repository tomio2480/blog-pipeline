# prompt-maker PR で得た知見：バリデーション実装とレビュー対応

## 背景

`scripts/prompt-maker/` の追加 PR（#24）で，Gemini レビューへの対応中に
2 つの詰まりが発生した．いずれも再発防止できる性質の問題のため記録する．

## 判断と解決

### 1. 制御文字範囲を含む正規表現のヌルバイト混入

`validate_session_id()` に制御文字チェックを追加しようとして，
Python の文字列操作でソースファイルへ以下を書き込もうとした．

```python
re.compile(r'[\\/:*?"<>|\x00-\x1f]')
```

`\x00` が実際のヌルバイト（0x00）として解釈されてファイルへ埋め込まれた．
これにより `SyntaxError: source code string cannot contain null bytes` が発生した．

**採用した解決策：** 制御文字チェックを正規表現から切り出し，
`any(ord(c) < 32 for c in session_id)` で実装した．
これにより正規表現に制御文字範囲を書かずに済む．

**根本的な予防策：** ソースファイルを書き換える際は Edit ツールで直接編集する．
Python スクリプト・echo・文字列連結を経由する生成では，エスケープが狂うリスクを伴う．

### 2. 文字セットが重複するバリデーションの順序

`/` は traversal パターン（`../../foo`）と Windows 予約文字の両方に含まれる．
Windows 文字チェックを traversal チェックより先に配置したことが原因である．
`../../some/dir` が「上位ディレクトリ参照」ではなく「ファイル名として使えない文字」
として先に判定され，既存テスト 3 件が失敗した．

**採用した解決策：** バリデーション順序を意味的に具体的なものから汎用的なものへ並べ直した．

```
最大長 → 制御文字 → 絶対パス → traversal（..）→ Windows 予約文字
```

「パスの構造」に関するチェックを「文字種」チェックより先に置くことで，
エラーメッセージが実際の問題を正確に表す．

### 3. 旧コミットに紐づくインラインコメントへの返信 404

fix コミットをプッシュした後，reviewdog は旧コミット SHA に紐づけてインラインコメントを投稿していた．
そのコメントへ `gh api .../replies` で返信すると
"Parent comment not found" (404) が返った．

**採用した対応：** PR 本体コメント（`gh pr comment`）で全返信をサマリー投稿した．
新しいコミットをプッシュした後も，最新コミットに紐づく形で
インラインコメントへの返信自体は成功している（Gemini の第 2 ラウンドで確認）．
問題は reviewdog が **旧コミット SHA へ紐づけた** コメントに限る．

## 代替案と棄却理由

- `\x00-\x1f` を文字列 `"\\x00-\\x1f"` として埋め込む：
  最終的にファイルに書き込まれる文字列がどうなるか予測しにくくなるため不採用．
- Windows 文字チェックを traversal より先に置いたまま traversal テストを修正する案も考えられる．
  この場合はテストのエラーメッセージが実態を反映しなくなるため不採用．
