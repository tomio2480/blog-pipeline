# フォトライフ画像アップロード基盤の実装知見

はてなフォトライフへの画像アップロード基盤（Issue #45・PR #54）で得た知見を記録する．着手前の重複検出，外部仕様の裏取り，設計判断，レビュー対応の判断を扱う．

## 目次

- 背景
- 着手前の重複検出
- 外部仕様の裏取り
- 設計判断
- レビュー対応の判断

## 背景

ブログ記事 API 単体では画像を送れない．本文へ画像を載せるには，フォトライフ
AtomPub API へ画像をアップロードし，応答の f:id 記法を本文へ埋め込む必要がある．
本 Issue #45 はアップロードして f:id を得るまでの基盤を扱う．本文への設置は
別 Issue #46 とした．

## 着手前の重複検出

別の起票 Issue #47（`hatena_entry_id` のクォート書き戻し）は，着手前の確認で
実装済みと判明した．`upsert_frontmatter_field` は既に `quote` 引数を持つ．
新規 POST 経路と `--sync` 経路の双方が `quote=True` を渡していた．

判断として `git log -S "<導入した識別子>"` で導入コミットを特定し，起票
セッションと同一の流れで解決済みと確認した．重複実装を避けてクローズした．
着手前にコードと git 履歴を当たる手順が，無駄な再実装を防ぐ．

## 外部仕様の裏取り

フォトライフ AtomPub の仕様は思い込みで書かず，公式ドキュメントで確認した．
要点は次のとおり．

- PostURI は `https://f.hatena.ne.jp/atom/post`．認証は WSSE．
- リクエストのルートは Atom 0.3 名前空間 `http://purl.org/atom/ns#` を使う．
  ブログ API の Atom 2005 名前空間とは別である点に注意する．
- 画像は `<content mode="base64" type="image/...">` で送る．
- フォルダは `<dc:subject>`（Dublin Core 名前空間）で指定する．
- 応答は `<hatena:syntax>f:id:USER:XXXX:image</hatena:syntax>` を含む．
  本文へ埋める `[...]` 化は別 Issue #46 の責務とした．

名前空間がブログ API と異なるため，既存の送信処理を流用しつつエントリ生成は
専用関数として分けた．WSSE 生成 `build_wsse_header` と送信 `_send_entry` は
そのまま再利用できた．

## 設計判断

- 二重アップロード防止のキーは画像内容の SHA-256 とした．リネームや移動を経た
  同一画像も同一視できる．SHA-256 は内容識別の用途で認証ではない．
- 記録は JSON のマッピングファイルとし，最上位 dict とキー・値の文字列性を
  検証して破損を早期に弾く．サードパーティ依存ゼロの原則を維持した．
- 既定フォルダ名は `blog` とした．フォルダ未指定時もブログ用画像をまとめる．

## レビュー対応の判断

Gemini レビューの指摘について採否を理由付きで判断した．

- 採用: `json.JSONDecodeError` をパス付き `ValueError` へラップ．例外型は元々
  `ValueError` のサブクラスだが，ファイル名をメッセージへ含める本コードベースの
  慣習に未準拠だったため合わせた．
- 採用: `save_upload_map` で親ディレクトリを自動作成し `FileNotFoundError` を防ぐ．
- 不採用: `try/except OSError` での再ラップ．元の `OSError` が `errno` と
  パスを含み有益で，同型の再送出は実益が乏しいため見送った．
- 採用: f:id 抽出を正規表現から `ET.fromstring` + `findtext(".//{*}syntax")` へ
  変更．`{*}` ワイルドカードで接頭辞変更や書式差に影響されない．要素テキスト
  全体を取る用途のため `findtext` が適する．数値部を切り出す `extract_entry_id`
  は正規表現を据え置いた．

XML 解析ではセキュリティフックが `defusedxml` を推奨したが導入しなかった．
入力は認証済み HTTPS レスポンスで信頼境界の内側であり，標準ライブラリのみ・
サードパーティ依存ゼロの設計原則を持つためである．既存 `parse_collection_feed`
と同方針とした．CodeQL の Python 解析も `ET.fromstring` を XXE として
検出しなかった．
