# ドラフト本文への画像設置の実装メモ

ドラフト本文の Markdown 画像記法をフォトライフ画像と `figure` へ置換する実装（Issue #46）の設計決定と，実装時点で残した懸念を記録する．懸念は実害が出てから対処する方針とし，本ノートは備忘とする．

## 目次

- 背景
- 設計決定
- f:id 記法での alt 反映
- 残した懸念
- レビュー対応の学び

## 背景

ブログ記事 API 単体では画像を送れない．基盤 Issue #45 で画像のアップロードと f:id 取得までを実装した．本 Issue #46 は本文への設置を担う．本文の `![alt](path "caption")` を検出し，ローカル画像はアップロードして f:id 記法へ置換する．外部 URL は `<img>` へ置換する．いずれも `<figure>` / `<figcaption>` で包む．

## 設計決定

着手前にユーザーへ確認し，次のとおり決めた．

- caption が無くても常に `<figure>` で包む．構造を統一する．
- 外部 URL 画像は `<figure><img>` へ変換する．アップロードはしない．
- 画像サイズ指定（`w300` 等．検討事項 #3）は今回の対象外とする．
- alt はアクセシビリティ必須とし，欠落はエラーとする．ローカル画像はアップロード前に alt を検証し，無駄な通信を避ける．

## f:id 記法での alt 反映

検討事項 #2（f:id 記法で alt を反映できるか）は公式情報で裏取りした．はてなは 2017 年にフォトライフ記法へ `alt` と `title` オプションを追加している．書式は `[f:id:USER:XXXX:image:alt=代替テキスト]` とする．

オプション値はコロン（`:`）と閉じ括弧（`]`）を区切りに使うため，これらを alt に含めると記法を壊す．実装側で早期にエラーとして弾く．日本語の alt は全角コロン・全角括弧を使うため実害は小さいと判断した．

## 残した懸念

次の 2 点は実装時点で未解決だが，実害が出てから対処する方針とした．

- 検討事項 #1 は実投稿でしか確認できない．懸念は，`<figure>` の生 HTML ブロック内で `[f:id:...]` 記法がはてな Markdown モードで展開されるかである．現状は f:id を独立行に置き，展開される可能性を高めた．マージ前または初回投稿時に実機で確認する．
- 正規表現で置換するため，コードブロック内へ例示した `![](...)` も変換対象になる．標準ライブラリのみの原則で Markdown パーサを導入していないことが理由である．画像記法を本文へ例示する記事を書くときに顕在化する．

## レビュー対応の学び

PR #58 では gemini-code-assist のレビューを 4 巡受けた．パス処理の堅牢化が中心で，採否を理由付きで返信した．次の知見を得た．

- クロスプラットフォームのパス検証は実行 OS に依存しないようにする．Windows の `Path("/x").is_absolute()` は False を返す．`PurePosixPath` と `PureWindowsPath` の双方で解釈して判定する．
- ドライブ相対パス（`C:assets/x.png`）は `is_absolute()` が False だが `.drive` を持つ．放置すると `base_dir` が無視されるため `win.drive` も弾く．
- パーセントデコードは検証の前に行う．後だと `%2e%2e%2f` のエンコードされた親参照を見逃す．
- 正規表現の貪欲一致はバックトラックで丸括弧入りパスを正しく拾う．非貪欲は内側の `)` で先に切れて誤る．Bot の提案でも検証して採否を決める．
- `urllib.error.HTTPError` は `OSError` のサブクラスだが `str()` に応答ボディが出ない．個別に捕捉してボディを拾うと失敗理由が残る．
- 単一著者の private pipeline は入力が信頼境界の内側にある．Windows 禁止文字や最大文字数の検証は YAGNI と判断して見送った．
